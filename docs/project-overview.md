# Financial API Defense Lab

## 1. 프로젝트 개요

Java/Spring Boot 기반 금융 API에서 객체별 접근 제어 취약점을 예방하고, 비정상적인 접근을 탐지하며, AI Agent가 변경한 코드의 보안 요구사항을 자동 검증하는 프로젝트다.

실제 금융권 침해사고에서 드러난 인증·인가 및 보안 관리 문제를 참고하되, 외부 금융기관과 연동하지 않고 격리된 환경과 합성 데이터만 사용한다.

또한 Codex를 활용한 하네스 엔지니어링을 실습하여 보안 코드의 개발·검증·리뷰·오류 대응 절차를 개선하고 그 효과를 측정한다.

## 2. 해결할 문제

### 금융 API 보안

- 인증된 사용자의 타인 금융정보 무단 조회(BOLA)
- 제휴사의 위임 범위 초과 및 회수된 권한 재사용
- 접근 제어 코드 변경으로 인한 보안 결함 재발
- 무단 접근에 대한 감사·탐지 체계 부족

### AI Agent 개발 환경

- AI가 작성한 보안 코드의 정확성 검증 부족
- 작업 위험도와 무관한 일률적인 검증 비용
- 테스트·CI 실패의 분석·수정·재검증 절차 미흡
- 보안 테스트의 결함 탐지 능력 및 Agent 작업 효율 측정 부족

## 3. 업무 시나리오

고객이 자신의 계좌 기본정보와 거래내역을 조회하고, 특정 제휴사에 계좌별 조회 권한을 부여하거나 회수하는 가상 금융정보 조회 서비스다.

| 사용자 | 역할 |
|---|---|
| 고객 | 본인 금융정보 조회, 제휴사 권한 부여·회수 |
| 제휴사 | 위임받은 계좌와 범위 내에서 금융정보 조회 |
| 보안 담당 개발자 | 감사 이벤트, 탐지 결과, 보안 검증 결과 확인 |

조회 권한은 `ACCOUNT_READ`와 `TRANSACTION_READ`로 구분하며, 계좌별로 독립적으로 부여한다.

## 4. MVP 범위

### 금융 API 보안

| ID | 기능 |
|---|---|
| F01 | 고객 본인 계좌정보·거래내역 조회 |
| F02 | 제휴사에 계좌별 조회 권한 부여 |
| F03 | 제휴사 조회 권한 회수 |
| F04 | 객체 소유권·위임 권한·조회 범위 검증 |
| F05 | 접근 및 권한 변경 감사 기록 |
| F06 | 규칙 기반 반복 무단 접근 탐지 |

### 하네스 엔지니어링

| ID | 기능 |
|---|---|
| H01 | 작업 위험도 Low/Medium/High 분류 |
| H02 | 위험도별 테스트·리뷰 기준 적용 |
| H03 | 보안 회귀 테스트 자동화 |
| H04 | High 위험도 변경의 독립 Agent 리뷰 |
| H05 | 결함 주입 기반 보안 Evals |
| H06 | 테스트·CI 실패 분석 및 재검증 절차 |
| H07 | 작업 성공률·토큰·시간 등 효율 측정 |

## 5. MVP 제외 범위

- 실제 금융기관 API·실거래 데이터 연동
- 계좌 개설, 송금, 이체 및 결제
- 복잡한 고객 동의 화면 및 조직별 권한 관리
- 별도 인증 서버, 자동 계정 차단
- 실시간 보안 관제 대시보드
- 머신러닝 기반 탐지
- AI SAST·DAST Agent 자체 개발
- AI의 완전 자동 수정·배포

SAST·DAST 및 의존성 취약점 검사는 필요성과 실행 비용에 따라 단계적으로 검토한다.

## 6. 개발 단계

### Phase 1. 접근 제어

- 금융정보 조회 및 제휴사 권한 관리
- 인증·인가 및 DB 접근 제어
- 보안 요구사항 기반 자동 테스트

### Phase 2. 감사·탐지

- 접근 및 권한 변경 감사 이벤트
- 반복 무단 접근 탐지 및 SecurityAlert 생성

### Phase 3. 하네스 평가·개선

- 위험도 기반 검증 및 독립 리뷰 고도화
- 결함 주입 기반 Evals
- CI 실패 대응 및 Agent 작업 효율 비교

Codex의 기본 규칙과 필수 보안 검증은 Phase 1부터 적용한다.

## 7. MVP 완료 기준

- 정의된 정상·비정상 접근 제어 테스트 통과
- 권한 회수 완료 후 새로운 무단 조회 차단
- 접근·권한 변경 감사 이벤트 기록
- 탐지 규칙 충족 시 보안 이벤트 생성
- 결함 주입 평가 4개 이상의 탐지 결과 측정
- High 위험도 변경에 강화된 검증 적용
- 테스트·리뷰·Agent 작업 효율 결과 기록
- 주요 설계 결정과 검증 결과 문서화

## 8. 개발 원칙

- 보안 요구사항을 기준으로 구현하고 테스트한다.
- 불필요한 인프라 및 기술 도입을 피한다.
- AI 작성 코드는 독립적인 검증을 거친다.
- 테스트 삭제·완화로 보안 결함을 해결하지 않는다.
- 설계 변경 시 선택 이유와 대안을 기록한다.
- 모든 공격 실습은 통제된 격리 환경에서 수행한다.
