# Security Requirements

## 1. 목적

금융 API의 필수 보안 정책, 불변 조건, 테스트 및 Evals 기준을 정의한다.

본 문서는 구현 기술과 독립적인 보안 요구사항의 기준 문서다. 코드 변경 이후에도 명시적으로 변경 승인된 요구사항을 제외한 모든 불변 조건을 유지해야 한다.

## 2. 접근 권한 정책

### 사용자별 권한

| 요청 주체 | 허용 행위 |
|---|---|
| CUSTOMER | 본인 계좌정보·거래내역 조회, 본인 계좌 권한 부여·회수 |
| PARTNER | 명시적으로 위임받은 계좌와 조회 범위에 대한 읽기 |

### 조회 권한

- `ACCOUNT_READ`: 계좌 기본정보 조회
- `TRANSACTION_READ`: 계좌 거래내역 조회

두 권한은 독립적이며 한 권한이 다른 권한을 포함하지 않는다.

위임 권한은 계좌·제휴사·권한 종류 단위로 관리한다. 계좌 소유자만 위임 권한을 부여·회수할 수 있고, 제휴사는 재위임할 수 없다.

권한 회수가 커밋된 이후 시작한 새로운 조회는 회수된 권한으로 허용되지 않는다.

## 3. 보안 불변 조건

| ID | 항상 만족해야 하는 조건 |
|---|---|
| INV-01 | 인증되지 않은 요청은 보호된 금융정보에 접근할 수 없다. |
| INV-02 | 고객은 다른 고객 소유의 금융정보에 접근할 수 없다. |
| INV-03 | 제휴사는 명시적으로 위임받은 객체와 조회 범위에만 접근할 수 있다. |
| INV-04 | 권한 회수 완료 후 시작한 새 조회는 회수된 권한으로 허용되지 않는다. |
| INV-05 | 권한이 없거나 검증에 실패하면 접근을 거부한다. |
| INV-06 | API 응답에는 요청 주체에게 허용된 정보만 포함된다. |
| INV-07 | 접근 거부 및 권한 변경은 감사 이벤트로 기록된다. |

보안 변경으로 위 조건을 위반해서는 안 된다.

## 4. 기능별 요구사항

| ID | 요구사항 |
|---|---|
| SR-01 | 검증된 인증 주체를 사용하며 클라이언트가 제공한 주체 식별자를 신뢰하지 않는다. |
| SR-02 | 조회 대상 계좌의 실제 소유권 또는 유효한 위임 권한을 확인한다. |
| SR-03 | 제휴사·계좌·조회 범위 및 회수 상태를 함께 검증한다. |
| SR-04 | 계좌 소유자만 권한을 부여·회수하며 변경과 감사 기록을 원자적으로 처리한다. |
| SR-05 | API 응답에서 내부 정보 및 허용되지 않은 필드를 제외한다. |
| SR-06 | 주요 접근 허용·거부 및 권한 변경을 감사하고 토큰·금융정보 원문을 기록하지 않는다. |
| SR-07 | 반복적인 무단 접근을 탐지해 SecurityAlert를 생성하며 자동 차단하지 않는다. |

### 감사 실패 처리

- 권한 변경과 감사 기록 중 하나라도 실패하면 권한 변경을 커밋하지 않는다.
- 접근 거부 이벤트는 실패한 업무 트랜잭션과 분리해 기록한다.
- 필수 감사 저장에 실패하면 금융정보를 반환하지 않는다.
- 감사 저장소 자체가 장애를 일으킨 경우에도 접근을 허용하지 않으며 장애를 별도 운영 로그에 기록한다.
- 저장소 장애 시 감사 이벤트의 완전한 보존까지 보장하는 것은 MVP 범위 밖이다.

### 이상 접근 탐지

R-01은 인증된 동일 주체의 반복적인 객체별 권한 위반을 대상으로 한다.

잘못된 입력 형식이나 단순 인증 실패는 해당 규칙의 위반 횟수에 포함하지 않는다. 탐지 임계값 및 실행 주기는 [아키텍처의 이상 접근 탐지](architecture.md#7-이상-접근-탐지)에서 정의한다.

## 5. 접근 권한 매트릭스

초기 합성 데이터:

- 고객 A: A-01, A-02 소유
- 고객 B: B-01 소유
- 제휴사 X: A-01의 ACCOUNT_READ 보유
- 제휴사 Y: 위임 권한 없음

| 요청 | 기대 결과 |
|---|---|
| 고객 A → A-01 기본정보 | 허용 |
| 고객 A → B-01 거래내역 | 거부 |
| 고객 B → A-02 기본정보 | 거부 |
| 제휴사 X → A-01 기본정보 | 허용 |
| 제휴사 X → A-01 거래내역 | 거부 |
| 제휴사 X → A-02 기본정보 | 거부 |
| 제휴사 Y → A-01 기본정보 | 거부 |
| 제휴사 X → 회수된 A-01 권한으로 조회 | 거부 |

## 6. 필수 보안 테스트

| ID | 검증 내용 | 기대 결과 |
|---|---|---|
| SEC-01 | 인증되지 않은 금융정보 조회 | 거부 |
| SEC-02 | 고객 본인 계좌 조회 | 허용 |
| SEC-03 | 다른 고객 계좌 조회 | 거부 |
| SEC-04 | 유효한 위임 권한으로 조회 | 허용 |
| SEC-05 | 위임받지 않은 계좌 조회 | 거부 |
| SEC-06 | 허용되지 않은 거래내역 조회 | 거부 |
| SEC-07 | 권한 회수 후 새 조회 | 거부 |
| SEC-08 | 타인 계좌의 권한 부여·회수 | 거부 |
| SEC-09 | 허용되지 않은 응답 필드 | 미노출 |
| SEC-10 | 권한 정보 누락·검증 실패 | 거부 |
| SEC-11 | 반복 무단 접근 | SecurityAlert 생성 |
| SEC-12 | 감사 기록 내 민감정보 | 미노출 |

### 추가 통합 검증

| 검증 내용 |
|---|
| 변조·만료·잘못된 발급자 및 audience의 JWT 거부 |
| 동일 권한의 동시 부여에서 활성 권한 중복 방지 |
| 권한 회수와 조회의 동시성 |
| 권한 변경 중 감사 저장 실패 시 전체 롤백 |
| 접근 거부 이후 감사 이벤트 유지 |
| 인증·인가 오류 시 데이터 미노출 |

보안 테스트는 정상 허용과 비정상 거부를 모두 확인한다. 기대 결과는 구현 코드가 아니라 본 문서의 정책을 기준으로 관리한다.

## 7. 결함 주입 Evals

| ID | 주입 결함 | 기대 탐지 |
|---|---|---|
| EVAL-01 | 객체 소유권 검증 누락 | SEC-03 |
| EVAL-02 | 위임 계좌 범위 검증 누락 | SEC-05 |
| EVAL-03 | 회수된 권한을 계속 허용 | SEC-07 |
| EVAL-04 | 응답에 허용되지 않은 필드 포함 | SEC-09 |

평가 항목:

- 알려진 결함 탐지율 및 정상 사례 오탐
- Agent의 결함 식별 정확성
- 수정 후 보안 회귀 테스트 통과 여부
- 재수정 횟수, 토큰 사용량, 작업 시간

결함을 탐지하지 못한 사례도 그대로 기록한다. 결함 주입은 정상 배포 코드와 분리한 격리 환경에서만 수행한다.

## 8. AI Agent 보안 작업 규칙

- 인증·인가, 권한 조회 SQL, 보안 검증 변경은 High 위험도로 분류한다.
- High 변경에는 관련 보안 테스트, 전체 보안 회귀 검증 및 독립 리뷰를 적용한다.
- 테스트를 삭제하거나 기대값을 완화해 보안 결함을 숨기지 않는다.
- 검증 실패 시 원인을 분석하고 수정한 뒤 재검증한다.
- 보안 정책 완화와 필수 검증 변경은 사람의 명시적 승인 없이 적용하지 않는다.
- 검증을 완료하지 못한 작업은 완료로 보고하지 않는다.

구체적인 실행 절차와 자동화는 후속 하네스 설계에서 정의한다.
