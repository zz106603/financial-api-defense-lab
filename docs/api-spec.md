# API Specification

## 1. 공통 규칙

**Base Path:** `/api/v1`

모든 API는 JWT Bearer Token 인증을 사용한다.

```http
Authorization: Bearer <JWT>
```

- JSON 요청·응답 사용
- 객체 식별자는 UUID
- 시간 값은 ISO 8601
- 금액은 정밀도가 보존되는 숫자 형식
- 조회 응답 금액은 BigDecimal 기반 JSON 숫자로 소수 둘째 자리 정밀도를 보존하며, 시각은 UTC ISO 8601(`Z`)로 반환
- 인증 주체는 검증된 JWT를 기준으로 식별
- 계좌별 권한은 DB의 현재 상태에서 확인
- 존재하지 않거나 접근할 수 없는 계좌는 동일한 외부 응답 사용

### 권한

| 주체 | 허용 기능 |
|---|---|
| CUSTOMER | 본인 계좌·거래내역 조회, 권한 부여·회수 |
| PARTNER | 위임받은 계좌·거래내역 조회 |

제휴사는 권한을 부여하거나 회수할 수 없다.

## 2. 엔드포인트

| Method | Endpoint | 기능 |
|---|---|---|
| GET | `/accounts/{accountId}` | 계좌 기본정보 조회 |
| GET | `/accounts/{accountId}/transactions` | 거래내역 조회 |
| POST | `/accounts/{accountId}/grants` | 제휴사 권한 부여 |
| DELETE | `/accounts/{accountId}/grants/{grantId}` | 권한 회수 |

모든 경로 앞에 `/api/v1`을 적용한다.

5단계에서 두 GET을 구현했다. POST/DELETE 권한 변경 API는 후속 6단계다. 인증 주체는 JWT 검증 결과의 DB UUID·유형만 사용하며 요청 파라미터·헤더·추가 ID 클레임으로 변경할 수 없다.

## 3. 계좌 기본정보 조회

**GET /accounts/{accountId}**

### 인가·검증 조건

- CUSTOMER: 계좌 소유자
- PARTNER: 해당 계좌의 활성 `ACCOUNT_READ` 보유

### 성공 응답 — 200 OK

```json
{
  "accountId": "11111111-1111-4111-8111-111111111111",
  "bankName": "Test Bank",
  "maskedAccountNumber": "123-***-789",
  "balance": 1500000
}
```

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 계좌 ID 형식 |
| 401 | 인증 실패 |
| 403 | 허용되지 않은 요청 주체 유형 |
| 404 | 계좌 없음 또는 조회 권한 없음 |

내부 관리 정보와 불필요한 민감 필드는 응답하지 않는다.

## 4. 거래내역 조회

**GET /accounts/{accountId}/transactions**

### 요청

```http
GET /api/v1/accounts/{accountId}/transactions?page=0&size=20
```

### 인가·검증 조건

- CUSTOMER: 계좌 소유자
- PARTNER: 해당 계좌의 활성 `TRANSACTION_READ` 보유

`ACCOUNT_READ`만으로는 거래내역을 조회할 수 없다.

### 성공 응답 — 200 OK

```json
{
  "accountId": "11111111-1111-4111-8111-111111111111",
  "items": [
    {
      "transactionId": "22222222-2222-4222-8222-222222222222",
      "occurredAt": "2026-11-11T01:30:00Z",
      "amount": 50000,
      "description": "Test Transaction"
    }
  ],
  "page": 0,
  "size": 20,
  "hasNext": false
}
```

### 페이지 규칙

- page는 0부터 시작한다.
- page 기본값은 0이고 0~2,147,483,647의 정수다. offset은 long으로 계산한다.
- size 기본값은 20, 허용 범위는 1~100이다. 범위를 넘기면 400이다.
- 정렬은 거래 시각 내림차순, 같은 시각이면 거래 UUID 내림차순이다. 클라이언트 정렬 문자열을 SQL에 삽입하지 않는다.
- size+1행으로 hasNext를 판단하며 전체 건수를 별도 조회하지 않는다.
- 허용된 빈 계좌·마지막 페이지 이후는 200과 빈 items/hasNext=false를 반환한다. 권한 없는 빈 계좌는 404다.
- 페이지·정렬 조건으로 다른 계좌의 거래가 노출되어서는 안 된다.

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 페이지·조회 조건 |
| 401 | 인증 실패 |
| 403 | 허용되지 않은 요청 주체 유형 |
| 404 | 계좌 없음 또는 조회 권한 없음 |

## 5. 제휴사 권한 부여

**POST /accounts/{accountId}/grants**

### 요청

```json
{
  "partnerId": "33333333-3333-4333-8333-333333333333",
  "permission": "ACCOUNT_READ"
}
```

### 인가·검증 조건

- CUSTOMER만 요청 가능
- 요청 고객이 해당 계좌의 소유자여야 함
- 대상 제휴사가 존재해야 함
- permission은 ACCOUNT_READ 또는 TRANSACTION_READ
- 동일한 활성 권한 중복 생성 금지
- 부여 고객은 JWT 인증 주체에서 결정

### 성공 응답 — 201 Created

```json
{
  "grantId": "44444444-4444-4444-8444-444444444444",
  "accountId": "11111111-1111-4111-8111-111111111111",
  "partnerId": "33333333-3333-4333-8333-333333333333",
  "permission": "ACCOUNT_READ",
  "grantedAt": "2026-11-11T10:35:00+09:00"
}
```

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 요청 값 |
| 401 | 인증 실패 |
| 403 | CUSTOMER가 아닌 요청 주체 |
| 404 | 계좌 없음·소유권 없음 또는 대상 제휴사 없음 |
| 409 | 동일한 활성 권한 존재 |

권한 생성과 감사 기록은 하나의 트랜잭션으로 커밋한다.

## 6. 제휴사 권한 회수

**DELETE /accounts/{accountId}/grants/{grantId}**

### 인가·검증 조건

- CUSTOMER만 요청 가능
- 요청 고객이 계좌 소유자여야 함
- grantId가 해당 계좌에 속해야 함
- 다른 고객의 권한을 회수할 수 없음

### 성공 응답 — 204 No Content

응답 본문은 없다.

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 식별자 형식 |
| 401 | 인증 실패 |
| 403 | CUSTOMER가 아닌 요청 주체 |
| 404 | 계좌·권한 없음 또는 소유권 없음 |

이미 회수된 권한에 대한 반복 DELETE 응답(204 또는 404)은 구현 전에 확정한다.

권한 회수와 감사 기록은 하나의 트랜잭션으로 처리하며, 커밋 이후 성공 응답을 반환한다.

회수 완료 이후 새로운 조회 요청은 해당 권한으로 허용되지 않아야 한다.

## 7. 공통 오류 처리

| 상태 | 의미 |
|---|---|
| 400 | 요청 형식·값 오류 |
| 401 | 인증 실패 |
| 403 | 요청 주체의 기능 사용 권한 없음 |
| 404 | 객체 없음 또는 객체별 접근 권한 없음 |
| 409 | 중복 활성 권한 등 상태 충돌 |
| 5xx | 서버·DB·필수 감사 처리 실패 |

### 오류 응답 예시

```json
{
  "code": "RESOURCE_NOT_FOUND",
  "message": "요청한 리소스를 찾을 수 없습니다.",
  "requestId": "77777777-7777-4777-8777-777777777777"
}
```

### 보안 원칙

- 내부 SQL·스택 트레이스·세부 권한 관계를 외부에 노출하지 않는다.
- 객체 미존재와 무단 접근을 외부 404 응답으로 구분하지 않는다.
- 내부 감사 이벤트에는 필요한 판단 사유를 기록한다.
- 필수 감사 기록 저장 실패 시 보호된 금융정보를 반환하지 않는다.
- 요청 추적 ID는 서버에서 생성·관리한다.
- 권한 검증 실패를 정상 응답으로 처리하지 않는다.

### 보안 오류 응답

4단계에서 Spring Security 인증·역할 검증 오류에 아래 형식을 적용한다.

| 상태 | code | message |
|---|---|---|
| 401 | UNAUTHENTICATED | 인증이 필요합니다. |
| 403 | ACCESS_DENIED | 요청 권한이 없습니다. |
| 503 | SERVICE_UNAVAILABLE | 요청을 처리할 수 없습니다. |

응답은 `code`, `message`, `requestId` 필드를 갖는 JSON이다. 보안 오류 응답을 생성할 때 서버가 UUID 추적 ID를 생성해 본문과 `X-Request-Id` 헤더에 동일하게 반환한다. 클라이언트 추적 ID를 재사용하지 않는다. 401에는 `WWW-Authenticate: Bearer`를 반환한다. 토큰·상세 클레임·내부 SQL·예외 설명은 응답하지 않는다.

JWT의 주체 유형이 없거나 CUSTOMER/PARTNER 이외이면 401이다. 403은 인증을 완료한 고객/제휴사가 기능별 역할 제한에 걸린 경우다. DB에서 주체를 찾지 못하면 401이며, 주체 저장소 조회 자체가 실패하면 503이다. 5단계의 조회 API 오류·감사와 추적 ID는 아래 규칙으로 연결한다.

### 조회 API 오류·추적 ID

5단계 조회 API에는 위 보안 오류와 같은 JSON 구조를 적용한다.

| 상태 | code | message |
|---|---|---|
| 400 | INVALID_REQUEST | 요청 형식이나 값이 올바르지 않습니다. |
| 404 | RESOURCE_NOT_FOUND | 요청한 리소스를 찾을 수 없습니다. |
| 503 | SERVICE_UNAVAILABLE | 요청을 처리할 수 없습니다. |

계좌 UUID는 표준 36자 표현을 사용하며 대소문자는 구분하지 않는다. 축약 UUID, 잘못된 UUID·페이지 입력은 400이다. 미존재와 무권한은 같은 404 응답이며 내부 존재/인가 플래그를 반환하지 않는다. 금융 조회 또는 필수 감사 저장 실패는 503이고 응답에 금융정보·SQL·예외 상세를 포함하지 않는다.

조회 요청은 성공 시에도 서버 생성 `X-Request-Id`를 반환하고 동일 ID를 감사에 저장한다. 오류 본문 requestId도 같은 값이다. 클라이언트의 ID를 사용하지 않는다. 금융 응답은 보안 필터의 `Cache-Control: no-store`를 유지한다. 전체 경로의 감사·추적 확장은 후속 단계다.

## 8. 감사·탐지 연계

외부 감사·관제 API는 MVP에서 제공하지 않는다.

내부 모듈에서 다음을 처리한다.

- 금융정보 조회 허용·거부 감사 기록
- 권한 부여·회수 감사 기록
- 반복적인 무단 접근에 대한 SecurityAlert 생성

5단계에서는 인증된 계좌·거래 조회의 허용·거부만 먼저 감사한다. 한 SQL에서 실제 계좌의 존재와 인가를 평가해 감사 사유를 ACCESS_ALLOWED / OBJECT_ACCESS_DENIED / RESOURCE_NOT_FOUND로 구분하며, 외부 404는 구분하지 않는다. 계좌 UUID는 외부 비밀키 기반 HMAC 가명 참조로 기록하고 토큰·금액·계좌번호·거래 원문은 전달하지 않는다. 감사 커밋 완료 전에는 조회 성공 응답을 반환하지 않는다. 인증 실패·입력 오류의 감사와 권한 변경 감사·탐지는 후속 범위이며, 인증/입력 오류를 객체별 권한 위반으로 집계하지 않는다.

접근이 거부되거나 업무 트랜잭션이 롤백되더라도 가능한 범위에서 독립적인 감사 기록이 유지되어야 한다.

구체적인 감사 트랜잭션 및 탐지 규칙은 아키텍처의 [감사 이벤트 트랜잭션](architecture.md#감사-이벤트-트랜잭션) 및 [이상 접근 탐지](architecture.md#7-이상-접근-탐지)를 따른다.

## 9. 보안 검증

API는 [보안 요구사항](security-requirements.md)의 INV-01~07, SEC-01~12를 만족해야 한다.

특히 다음 항목을 통합 테스트로 검증한다.

- 정상·비정상 JWT 및 요청 주체
- 타인 계좌 조회·권한 변경 거부
- 위임 계좌 및 조회 범위 초과 거부
- 권한 회수 후 새 조회 거부
- 허용되지 않은 응답 필드 차단
- 감사 저장 실패와 동시성 처리

## 10. MVP 제외 API

- 로그인·회원가입·토큰 발급
- 계좌 개설·수정·삭제
- 거래 생성·이체·결제
- 제휴사의 권한 재위임
- 감사 로그 공개 조회
- 실시간 관제·자동 차단
