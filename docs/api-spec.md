# API Specification

## 1. 공통 규칙

**Base Path:** `/api/v1`

모든 API는 JWT Bearer Token 인증을 사용한다.

```http
Authorization: Bearer <JWT>
```

- JSON 요청·응답 사용
- 객체 식별자는 UUID
- 시간 값은 ISO 8601
- 금액은 정밀도가 보존되는 숫자 형식
- 인증 주체는 검증된 JWT를 기준으로 식별
- 계좌별 권한은 DB의 현재 상태에서 확인
- 존재하지 않거나 접근할 수 없는 계좌는 동일한 외부 응답 사용

### 권한

| 주체 | 허용 기능 |
|---|---|
| CUSTOMER | 본인 계좌·거래내역 조회, 권한 부여·회수 |
| PARTNER | 위임받은 계좌·거래내역 조회 |

제휴사는 권한을 부여하거나 회수할 수 없다.

## 2. 엔드포인트

| Method | Endpoint | 기능 |
|---|---|---|
| GET | `/accounts/{accountId}` | 계좌 기본정보 조회 |
| GET | `/accounts/{accountId}/transactions` | 거래내역 조회 |
| POST | `/accounts/{accountId}/grants` | 제휴사 권한 부여 |
| DELETE | `/accounts/{accountId}/grants/{grantId}` | 권한 회수 |

모든 경로 앞에 `/api/v1`을 적용한다.

## 3. 계좌 기본정보 조회

**GET /accounts/{accountId}**

### 인가·검증 조건

- CUSTOMER: 계좌 소유자
- PARTNER: 해당 계좌의 활성 `ACCOUNT_READ` 보유

### 성공 응답 — 200 OK

```json
{
  "accountId": "11111111-1111-4111-8111-111111111111",
  "bankName": "Test Bank",
  "maskedAccountNumber": "123-***-789",
  "balance": 1500000
}
```

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 계좌 ID 형식 |
| 401 | 인증 실패 |
| 403 | 허용되지 않은 요청 주체 유형 |
| 404 | 계좌 없음 또는 조회 권한 없음 |

내부 관리 정보와 불필요한 민감 필드는 응답하지 않는다.

## 4. 거래내역 조회

**GET /accounts/{accountId}/transactions**

### 요청

```http
GET /api/v1/accounts/{accountId}/transactions?page=0&size=20
```

### 인가·검증 조건

- CUSTOMER: 계좌 소유자
- PARTNER: 해당 계좌의 활성 `TRANSACTION_READ` 보유

`ACCOUNT_READ`만으로는 거래내역을 조회할 수 없다.

### 성공 응답 — 200 OK

```json
{
  "accountId": "11111111-1111-4111-8111-111111111111",
  "items": [
    {
      "transactionId": "22222222-2222-4222-8222-222222222222",
      "occurredAt": "2026-11-11T10:30:00+09:00",
      "amount": 50000,
      "description": "Test Transaction"
    }
  ],
  "page": 0,
  "size": 20,
  "hasNext": false
}
```

### 페이지 규칙

- page는 0부터 시작한다.
- size는 서버에서 상한을 제한한다.
- 기본값과 최대값은 구현 전에 확정한다.
- 페이지·정렬 조건으로 다른 계좌의 거래가 노출되어서는 안 된다.

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 페이지·조회 조건 |
| 401 | 인증 실패 |
| 403 | 허용되지 않은 요청 주체 유형 |
| 404 | 계좌 없음 또는 조회 권한 없음 |

## 5. 제휴사 권한 부여

**POST /accounts/{accountId}/grants**

### 요청

```json
{
  "partnerId": "33333333-3333-4333-8333-333333333333",
  "permission": "ACCOUNT_READ"
}
```

### 인가·검증 조건

- CUSTOMER만 요청 가능
- 요청 고객이 해당 계좌의 소유자여야 함
- 대상 제휴사가 존재해야 함
- permission은 ACCOUNT_READ 또는 TRANSACTION_READ
- 동일한 활성 권한 중복 생성 금지
- 부여 고객은 JWT 인증 주체에서 결정

### 성공 응답 — 201 Created

```json
{
  "grantId": "44444444-4444-4444-8444-444444444444",
  "accountId": "11111111-1111-4111-8111-111111111111",
  "partnerId": "33333333-3333-4333-8333-333333333333",
  "permission": "ACCOUNT_READ",
  "grantedAt": "2026-11-11T10:35:00+09:00"
}
```

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 요청 값 |
| 401 | 인증 실패 |
| 403 | CUSTOMER가 아닌 요청 주체 |
| 404 | 계좌 없음·소유권 없음 또는 대상 제휴사 없음 |
| 409 | 동일한 활성 권한 존재 |

권한 생성과 감사 기록은 하나의 트랜잭션으로 커밋한다.

## 6. 제휴사 권한 회수

**DELETE /accounts/{accountId}/grants/{grantId}**

### 인가·검증 조건

- CUSTOMER만 요청 가능
- 요청 고객이 계좌 소유자여야 함
- grantId가 해당 계좌에 속해야 함
- 다른 고객의 권한을 회수할 수 없음

### 성공 응답 — 204 No Content

응답 본문은 없다.

### 오류

| 상태 코드 | 발생 조건 |
|---|---|
| 400 | 잘못된 식별자 형식 |
| 401 | 인증 실패 |
| 403 | CUSTOMER가 아닌 요청 주체 |
| 404 | 계좌·권한 없음 또는 소유권 없음 |

이미 회수된 권한에 대한 반복 DELETE 응답(204 또는 404)은 구현 전에 확정한다.

권한 회수와 감사 기록은 하나의 트랜잭션으로 처리하며, 커밋 이후 성공 응답을 반환한다.

회수 완료 이후 새로운 조회 요청은 해당 권한으로 허용되지 않아야 한다.

## 7. 공통 오류 처리

| 상태 | 의미 |
|---|---|
| 400 | 요청 형식·값 오류 |
| 401 | 인증 실패 |
| 403 | 요청 주체의 기능 사용 권한 없음 |
| 404 | 객체 없음 또는 객체별 접근 권한 없음 |
| 409 | 중복 활성 권한 등 상태 충돌 |
| 5xx | 서버·DB·필수 감사 처리 실패 |

### 오류 응답 예시

```json
{
  "code": "RESOURCE_NOT_FOUND",
  "message": "요청한 리소스를 찾을 수 없습니다.",
  "requestId": "req-example-001"
}
```

### 보안 원칙

- 내부 SQL·스택 트레이스·세부 권한 관계를 외부에 노출하지 않는다.
- 객체 미존재와 무단 접근을 외부 404 응답으로 구분하지 않는다.
- 내부 감사 이벤트에는 필요한 판단 사유를 기록한다.
- 필수 감사 기록 저장 실패 시 보호된 금융정보를 반환하지 않는다.
- 요청 추적 ID는 서버에서 생성·관리한다.
- 권한 검증 실패를 정상 응답으로 처리하지 않는다.

## 8. 감사·탐지 연계

외부 감사·관제 API는 MVP에서 제공하지 않는다.

내부 모듈에서 다음을 처리한다.

- 금융정보 조회 허용·거부 감사 기록
- 권한 부여·회수 감사 기록
- 반복적인 무단 접근에 대한 SecurityAlert 생성

접근이 거부되거나 업무 트랜잭션이 롤백되더라도 가능한 범위에서 독립적인 감사 기록이 유지되어야 한다.

구체적인 감사 트랜잭션 및 탐지 규칙은 아키텍처의 [감사 이벤트 트랜잭션](architecture.md#감사-이벤트-트랜잭션) 및 [이상 접근 탐지](architecture.md#7-이상-접근-탐지)를 따른다.

## 9. 보안 검증

API는 [보안 요구사항](security-requirements.md)의 INV-01~07, SEC-01~12를 만족해야 한다.

특히 다음 항목을 통합 테스트로 검증한다.

- 정상·비정상 JWT 및 요청 주체
- 타인 계좌 조회·권한 변경 거부
- 위임 계좌 및 조회 범위 초과 거부
- 권한 회수 후 새 조회 거부
- 허용되지 않은 응답 필드 차단
- 감사 저장 실패와 동시성 처리

## 10. MVP 제외 API

- 로그인·회원가입·토큰 발급
- 계좌 개설·수정·삭제
- 거래 생성·이체·결제
- 제휴사의 권한 재위임
- 감사 로그 공개 조회
- 실시간 관제·자동 차단
